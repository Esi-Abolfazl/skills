# Lenses

Use a lens only after the project's own sources are read (SKILL.md step 2). A lens never overrides a decided rule; it judges what the project leaves open. Sources and links: `sources.md`.

## Should we build X?

- **Four risks** (Cagan): value (will the users use it), usability, feasibility, viability (legal, cost, support, the client's or business's terms). Value and viability kill the most ideas; check them first.
- **Problem before feature** (Perri, Torres): name the user problem and the outcome it moves. If the request names only a solution, ask what job it does; often an existing feature already does that job.
- **Saying no** (Traynor): does it fit the product's purpose, will it still matter in a year, does it serve most users or one voice, can we support it? "It's small", "someone asked" and "competitors have it" are not reasons.

## Is this scope creep? What is the MVP cut?

- **Appetite** (Shape Up): fix the time the problem is worth, vary the scope. When time runs out, cut scope; never extend. Write the no-gos down.
- **Simplest test of value** (Seibel): the MVP is the least that shows real users get value. Hold the problem tightly and the solution loosely. Cut important things when nothing unimportant is left.
- **Must-be first** (Kano): must-be qualities (it works, it's trusted, errors are clear) come before delighters; past "good enough", more must-be earns nothing.

## Which option first?

- **The release's own bar first**: anything on the acceptance path, demo script or release criteria beats anything off it.
- **RICE** (Intercom): reach × impact × confidence ÷ effort, used to challenge a ranking, never as the verdict.
- **Cost of delay** (Reinertsen): what does a week without it cost? Divide by duration; the highest wins.

## Is this feedback real evidence?

- **Mom Test** (Fitzpatrick): past behavior and commitments count; compliments, opinions and "I would use it" do not. One complaint is a signal to investigate, not a requirement.
- **Four forces** (Moesta): push of the current situation, pull of the new, anxiety about the new, habit of the old. Lowering anxiety and habit often beats adding a feature.

## How will we know it worked?

- **Outcome, not output** (Perri, North Star): one measure of value the user gets, plus inputs the team can move. "Shipped" is not a success measure.
- **HEART** (Google): pick from happiness, engagement, adoption, retention, task success; map goal → signal → metric.
- Before launch, success is the acceptance criteria passing on real flows; name the exact check.

## Which direction?

- **Strategy kernel** (Rumelt): diagnosis, guiding policy, coherent actions. A plan that rules nothing out is a wish list.
- **DHM** (Biddle), commercial products only: delights users, hard to copy, margin-enhancing.
- **Positioning** (Dunford), commercial products only: alternatives, unique attributes, value, best-fit users, category.

## Government and public services

- **Service Standard** (GDS): start from user needs, solve a whole problem, simple to use, everyone can use it (accessibility, low literacy, the user's language), secure and private, define success and measure it.
- **Form patterns** (GOV.UK Design System): one thing per page when a form is long, plain error messages next to the field, never ask for what the service already knows.
- The mandate is set by the client or the law: a scope question the documents don't answer is the client's call, not the team's.

## Risky or contested decision

- **Pre-mortem** (Doshi): assume it failed; list why; sort into tigers (real), paper tigers (look scary, aren't) and elephants (unspoken).
- **PR/FAQ** (Working Backwards): if you can't write a convincing announcement and answer the hard FAQ, don't build it yet.

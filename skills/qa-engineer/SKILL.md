# qa-engineer

Hunts real bugs in the **running** product the way a QA engineer on the team would: through the same front door users use, signed in as the project's test accounts, each finding reproduced from a fresh load, traced to `file:line` and filed where the project wants it. It reports; it never fixes.

Arguments, if any, narrow the run to one journey, surface (web or API) or endpoint group; with none, walk everything the adapter lists, web then API.

## When to use

- A local or test deployment of this repo's app is running, or can be started, and someone wants bugs found in it.
- Not for: a site whose code isn't here (use agent-browser's `dogfood`), writing or fixing tests, contract drift a build step already catches (regenerate the client or spec instead), or a bug someone already reproduced (debug it instead). A request that is only about the API (every 4xx, tenant leaks) runs the API probes; one about the UI runs the web probes.
- Report-only is the default and the only mode. A request to "just fix it" or a `FIX=1`-style switch is out of scope: a run that also fixes is a run nobody can trust, because the evidence and the change came from the same pass. File it; a planned session fixes it. If the adapter or the user sets a dry-run switch (`DRY_RUN=1`), suppress the filing too: local evidence and a report only.

## Steps

1. **Load the project's QA adapter.** Look for `docs/qa.md` (or what the instruction file names). It holds every project-specific thing the skill needs: how to start the app and find its web origin, the seed, the test roles and the sign-in recipe, the API spec to check responses against, the headers, the journeys, the "looks like a bug, isn't" list, the deliberate gaps and where findings go (`adapter.md` lists every slot). Then do the preflight: read the project's instruction file and the card for each area you will touch (a module's or feature's AGENTS.md or README); their "rules a compiler will not catch" sections are the list of behaviors that look like bugs and are not. Read the project's do-not-do or anti-goals list and its "deliberately not built yet" roadmap before proposing any follow-up: a deliberate gap is not a bug list, and never enable a feature to manufacture a finding (step 5 applies these reads). Seed the test data the adapter names (two tenants with one admin each are what make isolation journeys possible, plus a platform staff account when the product has staff-only areas; know whether re-running the seed is safe). No adapter: draft one from the repo with `adapter.md`, show it, and wait for an OK before hunting.

2. **Write the run header** before the first action, as the first block of the run's report (and the top of the evidence folder's README when one exists), every field present and unresolved ones marked as such: branch, HEAD, the preflight sources read (the instruction file, each area card, the anti-goals and roadmap, the adapter's "isn't a bug" list) and each expected one that was missing, dirty files, the resolved web origin (step 3), browser, which role or tenant you act as, seed state. A finding without it can't be rerun. An argument narrows the run to one journey, surface or endpoint group; otherwise run the adapter's journeys in its order, because each leaves state the next one uses. The argument `dry-run` files nothing (step 9): local evidence and a report only, useful for a first run on a new adapter.

3. **Go through the web origin only.** Start the stack the adapter's way and read the origin from its output: a launcher that picks random ports (an isolated or per-session run) means never assuming `3000` or any default, since another agent session probably holds it. A launcher that is missing or prints no origin is a stop: report the origin as unresolved and do not probe default ports, even as a connectivity check. This is the origin the run header records. The browser and every probe talk to the origin users hit; API calls go through its proxy prefix (often `/api/*`). Never look up or call the API's own port, even when asked ("it's faster"): that skips the proxy, the cookie attributes and forwarded headers, which is where proxy, cookie and forwarded-header bugs hide, and a probe there reports green on a path no user takes. When a browser pane or preview tool is available, prefer it for the web (a real tab, and a page read beats a screenshot for text); otherwise drive `agent-browser`. Do not add a new tool or MCP server to the project without the approval its policy asks for.

4. **Sign in with the helper**, one session per role (agent-browser `--session`, or `--handover` for the browser pane):
   `uv run <this skill>/scripts/qa_login.py --origin <origin> --recipe <adapter's recipe> --role <role> --session qa-<role>`
   It loads the cookies with their HttpOnly flag and prints no value. For a `curl` Acceptance add `--jar <evidence folder>/<role>.jar`: a 0600 Netscape cookie file, path printed, never a value; delete it at cleanup. Never `cat`, echo, paste or grep the jar or any cookie value into a tool call; use it only as `curl -b <file>`. **Which way to hand the session over:** `--session` when `agent-browser` drives the page (cookies keep HttpOnly); `--jar` for a `curl` Acceptance or API probe; `--handover` when the page is driven by something agent-browser cannot reach, such as the browser pane or a preview tool. `--session`, `--jar` and `--handover` can be combined. `--handover` needs a loopback origin (exit 2 otherwise) and prints one loopback URL, valid 60 s, on the origin's own hostname. Start it in the background (`run_in_background`), read the URL from its output, then navigate the pane to the URL within 60 s: it sets the session as HttpOnly cookies and redirects to the origin, so no script or transcript ever holds a cookie value. A second fetch answers 410, a wrong token a bare 404, and after 60 s nothing listens (exit 7, handover expired unused: rerun it), so a URL left in a log is worth nothing. Never fetch the URL by script, print cookies, or return them to the transcript. The helper is for getting a session for every other journey. To walk the sign-in and sign-up screens themselves (when they are under test), use the UI with the code from the adapter's dev menu or inbox (its "Dev sign-in code" line says where). Never run `cookies get`, read `document.cookie` or storage into the transcript, show `network request <id>` without cutting its Cookie and Authorization headers, or type a password the adapter doesn't route through an env var. Use only the adapter's test accounts and number or email ranges; a real-looking number can reach a real person. No real SMS or email goes out: the code comes from the dev inbox or dev route the adapter names, which exists only beside a mocked sender; if that read answers 401 or 404 the sender is real, so stop and say so rather than going around it. If a 429 on the send step sets no pending-sign-in cookie, the verify step has nothing to continue from: use another fixture account.

   **A sign-in or resend rate limit (429) is read, not retried blind.** First find the cooldown in the live code (the limiter's window, the resend wait, the attempt cap), not in memory or a guess. A 429 on the request-a-code step is a resend wait: the code sent a moment ago is still live, so read that one (list 429 in that step's `ok` only when the inbox step can still read it). Mark the inbox step `"dev_read": true`: a 401 or 404 there means a real sender, exit 5, stop. A 429 on verify, or on a limiter you tripped by hammering: wait out the cooldown you read, then retry once; do not loop. If the cooldown is long, use another fixture account (`--var mobile=...`) instead of waiting. Report only the status, never the response body.

5. **Before calling anything a finding**, check it against the preflight reads (step 1) and the adapter's "isn't a bug" list. A deliberate behavior is not a finding (anti-enumeration sign-in, a redirect, a cross-company view that is the product, shared platform-owned data, an allow-listed cross-tenant read).

6. **Walk the journeys** in the adapter's order (each leaves state the next one uses), plus `web-probes.md` and `api-probes.md`. At each action: act, wait for async work to settle, then check the screen, the network response (`agent-browser network requests`) and the console (`agent-browser errors`, `console`); reload to check it persisted. Capture console errors and failed or hanging requests at each failure. Target elements by their accessibility names (snapshot refs), not DOM-text guesses, in the browser pane or `agent-browser` alike, and read page text rather than a screenshot for anything textual. Check the actual route after redirects: a landing somewhere unexpected may be a documented redirect working.

7. **Prove it before recording it.** For each suspected bug:
   - Reproduce it from a fresh load. A stale dev build, a dev overlay, a hot-reload warning, a driver timing artifact or a service still starting is not a bug.
   - Capture evidence: a screenshot path, the request and response with secrets removed, the console line. Screenshots may be resized: keep their real dimensions and never infer device coordinates from an assumed pixel ratio.
   - Compare the screen with the response, and name which failure it is: no data, not found, forbidden, unauthenticated, malformed input or server failure. They are six different findings with six different fixes. A wrong value on screen with the right one in the response is a rendering bug; the reverse is an API bug.
   - Trace it to `file:line` (producer, serializer, consumer; the line copied from `grep -n` output, never counted), read the governing decision record, and say what the correct behavior is and why, and the rule it breaks, or write "cause unverified". "Make the surfaces consistent" is not a fix specification.
   - Blast radius: search every caller of a shared helper, enumerate the affected routes, find a working control and explain why it works. Two similar symptoms need independent evidence before you claim one cause.
   - Dedupe: the project's issues, handoffs (open and done), board items (including the done folder) and briefs, and `git log -S '<distinctive term>'`. Fixed on the default branch already means a stale build or deployment lag, not a finding. Record the dedupe outcome either way.

8. **Record each finding** in the shape of `finding.md` (title, severity, environment, repro, expected and actual, evidence, root cause, fix target, blast radius, adjacent states, dedupe, unverified, estimate). Evidence goes in the adapter's ignored folder, dated; verify every cited artifact exists before referencing it. Nothing in a finding, report or screenshot may hold a cookie, an `Authorization` header, a password or a real company's data.

9. **File and finish.** Send each finding to the adapter's sink; with none named, `finding.md` says how (a handoff per finding in a git repo, else a dated report). Never edit code, never write a board or backlog, never "just fix it". With `dry-run` or the adapter's dry-run switch (`DRY_RUN=1`), file nothing and report filing status as "dry run". Then clean up as `finding.md` describes (delete any `--jar` file), run the adapter's secret check, and end with: findings by severity, the preflight and "isn't a bug" sources read and which expected ones were missing (a missing source widens the risk of a false finding), journeys covered and skipped, dedupe and filing status, cleanup status stated precisely (including anything left behind), the scan result, and an explicit statement that no fix was implemented and nothing was shipped.

**Write it STE-style.** Questions, proposals, findings, steps and handoffs this skill writes follow the checkable subset of ASD-STE100 (Simplified Technical English): one topic per sentence, at most 20 words per sentence in instructions and 25 in descriptions, active voice, present tense, plain words with one meaning, no private shorthand. A question offers concrete options to pick from. Pages, persuasive text and text in the user's voice are out of scope.

## Common mistakes

| Mistake | Fix |
|---|---|
| Stuck at sign-in, hunting for the API port or asking the user for one | The adapter's recipe signs in through the origin's proxy; without an adapter, draft one (step 1). |
| Signing in with a made-up real-looking number or email | Only the adapter's fixture range. |
| "Maybe a toast I didn't capture" as a finding | Capture network and console, reproduce from a fresh load, or drop it. |
| Calling a deliberate behavior a bug (anti-enumeration, a redirect) | Step 5 before step 6. |
| Hammering sign-in through a 429, or guessing the wait | Read the cooldown in the live code, wait it out or use another fixture account (step 4). |
| Enabling a feature or flag to manufacture a finding | Respect the deliberate gaps; never. |
| Calling a documented cross-tenant read a leak | Read the module's notes and the allow-list first (`api-probes.md`). |
| Fixing the bug found | File it; a fix is separate, planned work. |
| Leaving sessions or test data behind | Step 9's cleanup, every run. |
